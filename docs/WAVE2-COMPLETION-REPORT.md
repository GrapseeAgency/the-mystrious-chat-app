## 9. HARDWARE-DEPENDENT LIMITATIONS (honest)
- **Microphone/audio NOT hardware-verified.** No microphone exists in this sandbox: recording (MediaRecorder/AVAudioRecorder), playback (MediaPlayer/AVAudioPlayer) and the runtime permission flows are code-verified + compile-verified + pure-logic unit-verified (rounding, floors, rate cycles, state machines) — but NO real capture/playback was exercised. **Real-device verification (both platforms) remains REQUIRED before final release acceptance**, per the Wave 2 mandate.
- **ASR transcription**: route, auth, validation and the 200/cache-hit contract are proven; actual speech→text was not exercised (non-speech fixture → honest 502 from the speech service). Needs real speech audio (device or crafted fixture) to confirm end-to-end.
- iOS Wave 2 UI: compile-gated via CI (no local Swift toolchain in the sandbox) + launch smoke; instrumented UI interaction beyond the smoke was not performed.
- View-once anti-replay is client-side hardening; the backend still stores media (frozen backend — documented decision).
- Android voice speed chip hidden below API 23 (`setPlaybackParams` floor).

## 10. REMAINING MESSAGING GAPS
- Poll revote: API allows vote-move, native UI (like web) blocks after picking — product decision pending.
- Topic deletion UI not built natively (server + web support; native room self-heals when a topic disappears).
- Voice/view-once sends are online-only by design (Web parity) — they do not queue in the outbox.
- Saved library is capped by the server at 100 items (no pagination exists on the wire).
- Group view-once: first viewer burns for everyone (single `viewedAt` column — server truth).
- Deep links (`pulse://`) remain inert on Android (declared, unparsed) — carried over from Wave 1.
